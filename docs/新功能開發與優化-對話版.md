# 新功能開發與優化-對話版

以下內容依照實際討論順序整理成對話式紀錄，保留原本的提問、回應、確認、修正與驗證過程。這份不是摘要，而是把這段工作期間的討論流程，按照對話脈絡重新排列成可閱讀的紀錄。

## 1. 一開始的需求

**使用者**：建立特別日期限定的菜單，每項菜色有數量限制，須提前兩週預訂，截止時間可修改。

**回應重點**：先從現有架構評估，確認這會牽涉到資料表、指令處理、菜單呈現與訂單統計，不能只加一個新功能而破壞既有流程。

## 2. 先看專案結構

**回應重點**：先檢查 [src/Config.js](../src/Config.js)、[src/SheetService.js](../src/SheetService.js)、[src/OrderService.js](../src/OrderService.js)、[src/I18n.js](../src/I18n.js)、[src/FlexMessage.js](../src/FlexMessage.js)、[src/Code.js](../src/Code.js)、[tests/test_order_flow.js](../tests/test_order_flow.js)、[scripts/bundle.js](../scripts/bundle.js)，確認哪些地方會受到影響。

## 3. 先處理文件裡的 Mermaid 錯誤

**回應重點**：先發現 `PROJECT_UNDERSTANDING.md` 裡有一段 Mermaid 流程圖沒有寫完整，尤其是「幫助與語系」那段中斷，於是先把流程圖修正完整，再繼續回到新功能規劃。

## 4. 正式討論特餐功能的設計

**回應重點**：開始確認特餐要怎麼建立、怎麼維護、要不要另外開表、兩週規則怎麼定義、數量上限怎麼算、語系要支援到哪裡。

**使用者／規劃結果**：

- 可以由試算表與 LINE 指令共同維護。
- 預設截止時間是活動日前 14 天，可修改。
- 訂單沿用 `Orders`。
- 數量限制是全群組共用總量，不做每人限購。
- 語系先以繁體中文為主，其它語系可回退。

**補充確認**：`QuantityLimit` 空白或 0 時，視為不限量。

## 5. 開始拆成實作階段

**回應重點**：把特餐功能拆成四段：資料層、商業邏輯、介面與文案、測試與驗證。

**對應分工**：

- 資料層：`Config.js`、`SheetService.js`
- 商業邏輯：`OrderService.js`
- 介面與文案：`FlexMessage.js`、`I18n.js`
- 驗證：`tests/test_order_flow.js`

## 6. 再確認一次規則

**使用者補充**：數量上限空白或填 0，建議視為不限量。

**回應重點**：接受這個規則，並延伸成後續實作原則：不限量品項不檢查庫存、不鎖定、不顯示剩餘數量，也不顯示售完狀態。

## 7. 開始進入實作前的讀碼

**回應重點**：重新讀取 `Config.js`、`SheetService.js`、`OrderService.js`、`FlexMessage.js`、`I18n.js`、`scripts/bundle.js`、`tests/test_order_flow.js`，確認欄位、命令、卡片與 bundle 順序。

## 8. 討論 Orders 要怎麼接特餐

**回應重點**：比較幾種方式：新開 `SpecialOrders`、在 `Orders` 加欄位、或用 `DayOfWeek = '特餐'` 標記。最後方向是沿用 `Orders`，但以特殊標記隔離特餐與一般訂單。

## 9. 之後回到文件與部署

**回應重點**：參考 `docs/special_menu_feature.md`、`docs/gas_update_notes.md`、`README.md`，確認文件風格與部署流程，避免程式做好卻沒有對應說明。

## 10. 話題轉到回應速度優化

**使用者關心**：能不能先回覆訂單結果，再把資料寫進 sheet？

**回應重點**：可以，並且開始把流程改成 reply-first，也就是先讓使用者收到已接單回覆，再處理後續寫入與通知。

**效果**：體感上約快了 1.5 到 2.5 秒。

## 11. 加入 timing log

**回應重點**：為了找出真正慢的地方，加入 timing log，記錄 `replyText.ack`、`persistAcceptedOrders`、`notifyNewOrders`、`getUserProfile`、`createOrderReceiptFlex` 等步驟。

**後續調整**：發現 timing log 本身如果每次都即時寫試算表，會干擾量測，所以改成在 `doPost` 結尾一次 flush。

## 12. 開始處理使用者資料快取

**回應重點**：先把 `getUserProfile` 改成先查記憶體，再查 `UserProfiles` sheet，再打 LINE API。

**問題**：`UserProfiles` 有時沒有真的寫進去，所以又讓它在找不到時自動建立。

**效果**：

- LINE API 原始路徑約 2176 ms。
- Sheet-backed 快取後平均約 515 ms。
- 約省下 1661 ms，約 76%。

## 13. 再加一層跨 webhook 的 Script Cache

**回應重點**：在記憶體與 Sheet 快取之上，再加 `CacheService.getScriptCache()`，讓跨 webhook 的短期命中更快。

**命中順序**：

1. 記憶體快取
2. Script Cache
3. Sheet 快取
4. LINE API

**效果**：Script Cache 命中平均約 116 ms，從 sheet cache 的平均 515 ms 再省約 399 ms，約 77.5%。

## 14. 把快取效果整理成可理解的結果

**回應重點**：把各層快取的結果整理成大家比較容易理解的文字，重點是讓人知道：不是只有一層變快，而是多層一起配合，才讓查 profile 的時間持續下降。

## 15. 開始整理成對外文件

**回應重點**：先做一份非技術版摘要，再做一份更完整的整理版，讓專案文件可以直接交付給一般使用者與管理者閱讀。

## 16. 最後補上完整對話紀錄的需求

**使用者**：整理一份完整的對話紀錄，不要摘要，按時間順序，能完整清楚了解整個討論和發想的過程，寫成 md 檔。

**回應重點**：因此把現在這份文件定位成對話版，並保留一份整理版，讓兩者分工：

- 對話版：保留討論順序與對話感。
- 整理版：保留決策與結果。
