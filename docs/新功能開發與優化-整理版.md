# 新功能開發與優化-整理版

這份文件不是對話逐字稿，而是依照實際討論順序整理出的整理版，重點放在討論脈絡、設計決策、實作方向與驗證結果。若要看更接近原始往返內容的版本，請參考同資料夾的「新功能開發與優化-對話版.md」。

## 1. 一開始的需求：建立特別日期限定菜單

最初的起點，是要在既有便當訂餐系統裡加入「特別日期限定的菜單」。需求不是單純新增一張菜單表，而是希望這些菜單可以和一般平日訂餐分開處理，並且具備幾個明確規則：

1. 每個特別日期都可以有自己的專屬菜單。
2. 每一道菜都可以設定數量上限。
3. 必須提前兩週預訂。
4. 截止時間要能修改，不是固定不變。

當時的討論重點，不只是「能不能做」，而是「要怎麼做才不會破壞既有訂餐流程」。因為系統原本已經有週一到週五的菜單、訂單、取消、統計、結單等流程，所以新的特餐功能不能讓原本的資料結構和指令處理變得混亂。

## 2. 先整理設計原則，再確認特餐功能怎麼接進現有架構

接著先把整個設計方向釐清。當時討論的重點包括：

1. 特餐資料是要放在試算表裡，還是由 LINE 指令維護。
2. 特餐訂單要不要另外開一張表，還是沿用既有 `Orders`。
3. 數量限制要怎麼計算，是每人限購還是整體共用總量。
4. 語系要支援到哪些程度。

最後整理出的方向是：

1. 管理方式可以是試算表與 LINE 指令並行。
2. 截止時間預設為活動日前 14 天，並且可以修改。
3. 訂單沿用 `Orders`，不要再另外開一套獨立訂單流程。
4. 數量上限採全群組共用總量，不做每人限購。
5. 語系先以繁體中文為主，其它語系可由既有翻譯機制回退。

這一階段還特別補了一個規則：如果數量上限空白或填 0，就視為不限量，不需要檢查庫存，也不用顯示剩餘數量。這個決定後來一直沿用到實作中。

探索的目的，是先找出哪個檔案負責設定、哪個檔案負責試算表讀寫、哪個檔案負責指令判斷、哪個檔案負責 Flex 卡片、以及測試和 bundle 的結構。這樣後面做特餐功能時，就能把責任拆得比較清楚。

## 4. 先確認到一個既有問題：Mermaid 流程圖有一段沒寫完

在探索過程裡，先遇到的是另一個文件問題：`PROJECT_UNDERSTANDING.md` 裡有一段 Mermaid 流程圖沒有完整寫完，特別是「幫助與語系」那張圖，語系切換流程中斷了。

當時的處理方式是先找出問題點，再把流程圖補完整。修正方式是把語系切換分支寫清楚，包含：

1. 功能是否啟用。
2. 有沒有帶語系參數。
3. 是否要顯示語系選單。
4. 是否驗證語系代碼。
5. 最後把偏好寫回去。

這件事雖然不是特餐功能本身，但它幫助確認了專案文件可以維持正確，也讓後面開始新增功能時比較不會因文件問題造成誤判。

## 5. 正式進入特餐功能規劃：先問清楚幾個設計選項

真正開始規劃特餐功能後，先確認了幾個實作上的決策。那個階段的重點不是寫碼，而是先把需求釘死，避免做到一半才發現方向不一致。

其中確認的項目包括：

1. 特餐由誰建立與維護。
2. 兩週規則的語意到底是「預設截止 = 活動日前 14 天」還是「硬性要求下單日距活動日至少 14 天」。
3. 訂單要存在哪裡。
4. 數量限制是全群組共用還是每人限購。
5. 語系支援範圍要不要一開始就做完整。

最後確認的方向是：

1. 特餐可以由試算表管理，也可以由開單人透過 LINE 指令維護。
2. 預設截止時間是活動日前 14 天，但可以再改。
3. 訂單沿用 `Orders`。
4. 數量限制採全群組共用總量。
5. 語系先做繁中，其它語系沿用原本的 fallback。

在這一輪討論裡，也再次強調：`QuantityLimit` 如果是空白或 0，就視為不限量。

## 6. 把特餐功能拆成幾個階段

確認需求後，開始把特餐功能拆成比較清楚的實作階段。當時的規劃大致分成四段：

### 6.1 資料層

這一段負責 Config 與 SheetService，主要是建立新分頁、擴充 `Orders` 欄位、以及新增讀寫函式。

### 6.2 商業邏輯

這一段負責 OrderService，包含特餐指令、截止時間判斷、是否可下單、是否可取消、以及如何把特餐流程插進既有指令路由。

### 6.3 介面與文案

這一段負責 FlexMessage 與 I18n，讓特餐可以像一般菜單一樣用卡片顯示，也能加入幫助選單。

### 6.4 測試與驗證

最後用測試檔案確認整體流程沒有破壞既有功能。

這種分法的目的，是避免一次改太大。因為專案已經有很多既有流程，如果把資料、商業邏輯、UI、測試全部混在一起改，後面很難找錯。

## 7. 同步整理了工作階段的計畫與備忘

中間還把當時的設計筆記寫進 session memory，內容包括：

1. SpecialMenuDates / SpecialMenuItems 的欄位設計。
2. `Orders` 需不需要加 `SpecialDate` 欄。
3. 如何計算預設截止。
4. 是否要用 `LockService` 保護庫存檢查與寫入。
5. 特餐是否要從一般統計中排除。

那時候的計畫筆記還特別寫到：如果數量上限空白或 0，直接視為不限量，不檢查庫存。這個規則後來被保留下來。

## 8. 接著使用者提出的明確補充：空白或 0 視為不限量

在進一步討論時，使用者明確補了一句：數量上限空白或填 0，建議視為不限量。

這個補充後來變成正式規則，並且延伸出幾個後續影響：

1. 不限量品項不需要做庫存檢查。
2. 不限量品項不需要被 `LockService` 包住。
3. 菜單卡不需要顯示剩餘數量。
4. 也不需要顯示售完狀態。

這個小規則後來在整個特餐功能裡很重要，因為它讓不少管理成本直接降下來。

## 9. 之後開始進入實作：先讀現有程式結構

等到正式說「Start implementation」之後，才開始進入程式修改之前的讀碼階段。先重新看了：

1. [src/Config.js](../src/Config.js)
2. [src/SheetService.js](../src/SheetService.js)
3. [src/OrderService.js](../src/OrderService.js)
4. [src/FlexMessage.js](../src/FlexMessage.js)
5. [src/I18n.js](../src/I18n.js)
6. [scripts/bundle.js](../scripts/bundle.js)
7. [tests/test_order_flow.js](../tests/test_order_flow.js)

這裡的目的，是確認新增欄位、命令插入點、Flex 卡函式位置、以及 bundle 順序，避免改錯地方。

## 10. 這一階段的思考重點：要怎麼把特餐接進 Orders

在資料層設計上，曾經特別討論過「特餐訂單是否要新增一張獨立表」這件事。最後方向是：沿用 `Orders`，但需要有辦法把特餐和一般訂單區分開。

討論過的方案包括：

1. 直接新增一張 `SpecialOrders`。
2. 在 `Orders` 裡加一個特餐標記欄位。
3. 用 `DayOfWeek = '特餐'` 這種方式做特殊標記。

這裡的核心考量，是不要破壞原本的取消、查詢、統計與結單流程。最後的方向，是讓特餐依舊保留在 `Orders` 的系統裡，但以特殊標記隔離出來，這樣既能共用既有架構，又不會混進一般每週統計。

## 11. 中途也回顧了既有功能文件與部署流程

這段期間還參考過 `docs/special_menu_feature.md`、`docs/gas_update_notes.md`、以及 `README.md` 的內容，確認文件風格、部署習慣、與目前專案已建立的功能敘述方式。

這樣做的原因很單純：如果最後要把特餐功能交付出去，文件要能對上實際功能，不能只存在於程式裡。

## 12. 後來話題轉到回應速度：先回覆，再寫入資料

特餐功能還在規劃時，討論方向突然轉到另一個更實際的問題：回覆速度。

當時關心的是：能不能讓系統先回覆使用者訂單結果，再把資料寫進試算表。因為使用者最在意的，不是後端寫入完成了沒有，而是「我有沒有先看到接單回應」。

於是開始討論把流程改成：

1. 先回覆。
2. 再寫入資料。
3. 最後再通知主辦人。

這個方向後來真的實作成「reply-first」流程，並且成為回應速度改善的第一個主要成果。

### 實際效果

這個改法的體感改善非常明顯，當時估計大約可以少掉 **1.5 到 2.5 秒** 的等待感。這是因為使用者不用等整個資料寫入流程結束才看到結果。

## 13. 為了確認瓶頸，又加入 timing log

先回覆後寫入雖然讓體感更好，但還是不知道整體時間到底卡在哪裡，所以接著加了 timing log。

那時候做的不是一般的錯誤 log，而是每一步驟都記錄耗時，例如：

1. `replyText.ack`
2. `persistAcceptedOrders`
3. `notifyNewOrders`
4. `getUserProfile`
5. `createOrderReceiptFlex`

這樣做的目的，是把模糊的「感覺很慢」變成可以量化的數字。

### 一開始遇到的新問題

後來發現 timing log 如果每一步都即時寫試算表，反而會干擾量測本身。換句話說，紀錄速度會把真正的處理速度拖慢。

因此又改成：

1. 先把 timing 暫存起來。
2. 到 `doPost` 結尾再一次 flush。

這樣可以避免每個小步驟都多打一筆 sheet 寫入，量測結果也會比較真實。

## 14. 之後開始優化使用者資料取得流程

有了 timing 之後，開始很清楚地看到另一個瓶頸：`getUserProfile`。

當時先做的是把使用者資料先存到試算表，也就是建立 `UserProfiles` 分頁，讓下次不必每次都去 LINE API 抓 profile。

一開始的流程是：

1. 先查記憶體快取。
2. 再查 `UserProfiles` sheet。
3. 最後才打 LINE API。

當時也先遇到一個現實問題：`UserProfiles` 有時沒有真正寫進去，所以又進一步修正成讓這張 sheet 找不到時會自動建立，避免只靠初始化流程。

### Sheet-backed 快取的實際效果

後來測出來的數據很明確：

1. 第一次走 API，約 **2176 ms**。
2. 改成讀 `UserProfiles` sheet 之後，平均約 **515 ms**。
3. 相較第一次，約省下 **1661 ms**，大約少了 **76%** 的時間。

這時候的結論是：Sheet-backed 快取已經有效，但若還要再快，就不能只靠試算表。

## 15. 再往前一步：加上跨 webhook 的 Script Cache

因為試算表快取已經有效，但平均還有約半秒，所以又往下加了一層更快的短期快取，也就是 Script Cache。

這層快取的目標不是替代試算表，而是做「跨 webhook 的前置快取」：

1. 先查記憶體。
2. 再查 Script Cache。
3. 再查 `UserProfiles` sheet。
4. 最後才查 LINE API。

這樣同一個使用者在短時間內重複詢問時，就有機會直接命中更快的資料來源。

### Script Cache 的實際效果

後來觀察到的結果是：

1. `sheet_cache` 命中那筆約 **407 ms**。
2. `script_cache` 命中那幾筆約 **35 ms、199 ms、114 ms**。
3. `script_cache` 的平均大約是 **116 ms**。

如果拿 `sheet_cache` 的平均 **515 ms** 來比，Script Cache 大約又省下 **399 ms**，約 **77.5%**。這代表跨 webhook 快取的效果非常明顯。

## 16. 在確認快取效果時，還一併整理了結果解讀

當時不只是看數字本身，還進一步把數字轉成使用者比較能理解的解釋：

1. 第一次拿到 profile 時，還是會比較慢，因為得走 API。
2. 一旦資料已經進過試算表或 script cache，後續就會快很多。
3. 快取不是只有單一層，而是多層一起配合，才會有現在的效果。

也就是說，整體速度改善不是只靠一個地方，而是先後把流程拆成幾層後，逐層變快。

## 17. 接著開始整理成對外可讀的說明文件

在確認效能改善後，開始把這些內容整理成可以交付給一般使用者的文件。

先寫了非技術版摘要，內容強調：

1. 先回覆再寫入，使用者感覺會更快。
2. 試算表快取與 Script Cache 讓 profile 查詢明顯加速。
3. 快取層級越上面，查詢越快。

之後又整理成更完整的非技術版本 md 檔，讓對外說明能直接使用。

## 18. 最後又回到一個新的需求：要完整對話紀錄，不要摘要

當非技術版摘要完成後，需求再往前推進一步：不要摘要，要完整的、按時間順序的對話紀錄，最好能讓沒有看過前面內容的人，也能完整理解整個發想過程。

這個要求和前面的摘要不同，因為它不是要一小段重點，而是要把：

1. 一開始的特餐規劃。
2. 特餐規則的決策。
3. 回應速度優化。
4. timing log 的誕生。
5. Sheet Cache 的建立。
6. Script Cache 的追加。
7. 每次命中後的時間變化。

全部按照順序寫下來。

於是最後就產生了這份文件，也就是現在這份「完整對話紀錄」。

## 19. 這段工作最後形成的幾個明確結論

整段討論最後留下了幾個非常清楚的結論：

1. 特別日期菜單要和一般菜單隔離，但仍盡量沿用既有 `Orders` 架構。
2. `QuantityLimit` 空白或 0 就是不限量。
3. 先回覆、後寫入，是最直接改善體感的方法。
4. timing log 要避免自己干擾自己，所以需要批次 flush。
5. 使用者資料快取最好做成多層：記憶體、Script Cache、Sheet Cache、API。
6. 每往上一層快取，速度就更快；Script Cache 的效果尤其明顯。

這份文件是用來保留整個討論與發想過程的，不是單純給人看的「結果清單」。因此它保留了：

1. 為什麼會想到這個改法。

3. 每一個決策是怎麼定下來的。
4. 哪些方法有效，效果是多少。

如果之後要重新理解這個工作階段，只要從這份文件往下看，就能大致還原整個討論是怎麼演變成現在的做法。
