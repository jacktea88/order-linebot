# 新功能開發與優化-非技術版

這份摘要整理了本次工作階段的主要調整，以及幾種加快回覆速度的方法與效果，方便交付給非技術使用者閱讀。

## 一、這次做了什麼

本次主要完成三件事：

1. 新增「特別日期限定菜單」功能，讓特定日期可以設定專屬菜單、數量上限與截止時間。
2. 調整訂單處理流程，改成先回覆使用者，再把訂單資料寫入試算表，讓使用者感覺更快。
3. 逐步加入多層快取，減少每次都去查試算表或 LINE 服務的次數，進一步降低回應時間。

## 二、回覆速度的改善歷程

### 1. 先回覆，再寫入資料

原本系統會先等訂單資料寫完才回覆，使用者會感覺比較慢。後來改成先回覆「已收到訂單」，再把資料寫進試算表。

效果：

- 使用者的等待感明顯下降。
- 體感上大約快了 1.5 到 2.5 秒。

### 2. 加入 timing log，找出真正慢的地方

我們加了時間紀錄，先把每個步驟花多少時間量出來，確認瓶頸在哪裡。

效果：

- 可以看出慢的地方不只在回覆本身，還包含查使用者資料、寫試算表、以及建立收據內容。
- 這讓後續優化有明確方向，不是盲目猜測。

### 3. Timing log 改成一次寫入

原本每個步驟都會即時寫一筆紀錄，這本身也會拖慢速度。後來改成先暫存，最後一次寫入。

效果：

- 避免「記錄速度」干擾「實際速度」。
- 量測結果更接近真實情況。

### 4. 先用試算表快取使用者資料

接著把使用者資料先存到試算表裡，讓系統不用每次都去 LINE 重新查資料。

效果：

- 第一次仍可能需要查 LINE，但之後多數情況可以直接從試算表讀取。
- 之前完整查詢約 2.2 秒，改成試算表快取後平均約 0.5 秒。
- 等於大約省下 1.6 秒左右，約少了四分之三的時間。

### 5. 再加一層跨回合快取

後來又加上更快的短期快取，讓同一個使用者在短時間內重複詢問時，可以先從更快的地方直接拿資料。

效果：

- 命中短期快取時，查詢時間進一步降到約 0.1 秒上下。
- 與原本完整查詢相比，又再省下約 0.4 秒到 2 秒不等，視當次命中的層級而定。

## 三、各種方法的效果比較

| 方法 | 平均時間 | 改善幅度 |
| --- | ---: | ---: |
| 原始查詢 LINE 資料 | 約 2.2 秒 | 基準 |
| 試算表快取 | 約 0.5 秒 | 約快 1.6 秒 |
| 短期快取 | 約 0.1 秒 | 比試算表快取再快很多 |

## 四、目前的整體結論

目前系統已經不是每次都要重新查外部資料，而是會優先用快取結果，因此整體回覆速度比一開始明顯提升。

簡單來說：

- 使用者會更快收到「已接單」回覆。
- 重複查詢使用者資料時，速度已經明顯縮短。
- 系統也更容易維持穩定，不會每次都卡在外部查詢。

## 五、補充說明

這次的優化不是只靠單一方法，而是分成幾層一起做：

1. 先回覆，減少等待感。
2. 用時間紀錄找瓶頸。
3. 用試算表保存常用資料。
4. 再加上更快的短期快取。

因此目前的結果不是「某一個點突然變快」，而是整體流程都有變順。
